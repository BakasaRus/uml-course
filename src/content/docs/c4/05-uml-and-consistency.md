:::note[TL;DR]
C4 и UML не конкурируют. C4 даёт компактную архитектурную карту для выбранной аудитории, а UML формально описывает отдельные аспекты системы. Один и тот же элемент можно проследить между моделями, но эти нотации не образуют взаимно однозначного перевода.
:::

## Разные задачи

C4 отвечает на вопрос: **какой уровень архитектурного представления сейчас нужен и что на нём существенно?** UML отвечает: **какими семантическими средствами точно выразить конкретный аспект модели?**

Поэтому попытка заменить одну нотацию другой приводит к двум плохим вариантам: либо Context засоряется `include`, классами и портами, либо UML-диаграмма превращается в набор прямоугольников без семантики отношений.

| C4-представление | Источник в модели | Подходящие UML-представления |
| --- | --- | --- |
| System Context | граница, стейкхолдеры, внешние системы | [use case diagram](/notation/usecase-diagrams) для целей и акторов |
| Container | программная, системная и data architecture | [component](/notation/component-diagrams), [deployment](/notation/deployment-diagrams), [package](/notation/package-diagrams) по необходимости |
| Component | ответственность и контракты внутри одного приложения | [component](/notation/component-diagrams), [internal structure](/notation/internal-structure-diagrams), [technical class](/notation/technical-class-diagrams) |
| Code | техническая модель реализации | [technical class diagram](/notation/technical-class-diagrams) |
| Dynamic | сценарий или use case | [sequence](/notation/sequence-diagrams), [communication](/notation/communication-diagrams), [activity](/notation/activity-diagrams) |
| Deployment | инфраструктурное решение и среда | [deployment](/notation/deployment-diagrams), [deployment advanced](/notation/deployment-advanced) |

Таблица указывает полезные переходы, а не правила преобразования. Например, один C4 Container может быть реализован несколькими UML Components, packages и deployment artifacts; одна UML class diagram может обслуживать несколько C4 Components.

## Трассируемость

C4-карта должна опираться на существующие решения. Минимальная цепочка для сквозного примера может выглядеть так:

```text
Требование: студент не может записаться на занятый интервал
→ use case: «Записаться на консультацию»
→ сценарий: проверка доступности до создания записи
→ предметное правило: интервал не имеет двух активных записей
→ Container: Backend API и База записей
→ Component: Booking и Schedule
→ Dynamic: проверка и сохранение в сценарии записи
→ Deployment: экземпляр Backend API и БД в production
```

Не обязательно рисовать всю цепочку на одной диаграмме. Важно, чтобы вопрос «почему этот элемент существует?» имел ответ в требованиях, сценарии или ADR, а изменение существенного элемента было видно в связанных представлениях.

## Инварианты согласованности

Проверьте хотя бы следующие условия:

- граница System Context совпадает с границей в [модели стейкхолдеров](/modelling/stakeholders-and-boundary);
- C4 Container имеет понятную ответственность в [программной архитектуре](/modelling/software-architecture-and-layers) или [архитектуре данных](/modelling/data-architecture);
- каждый C4 Component принадлежит ровно одному container в рамках конкретной диаграммы;
- Dynamic view использует элементы статической C4-модели, а не вводит новые;
- Deployment view размещает экземпляры существующих systems и containers, а не новые логические части;
- внешняя система не становится внутренней между уровнями без явного изменения границы;
- сущностные имена и важные связи одинаково понимаются в требованиях, диаграммах и ADR.

Это частный случай общей [согласованности и трассируемости модели](/modelling/model-consistency-and-traceability). Там описано, почему внутренне правдоподобная диаграмма всё равно может быть неверна в контексте всей модели.

## Работа с изменениями

C4 особенно полезен как короткий обзор, но быстро устаревает, если обновлять его отдельно от решений. При изменении системы пройдите маршрут:

1. Изменилось требование, сценарий, граница или внешняя интеграция — обновите источник изменения.
2. Пересмотрите ADR, если меняется архитектурная альтернатива или её обоснование.
3. Обновите сначала Context или Container, если меняется граница либо крупная ответственность.
4. Обновите Component, Dynamic или Deployment view только при затронутой детализации.
5. Проверьте, что ссылки на UML ведут к модели, которая уточняет C4, а не противоречит ей.

Не создавайте C4-диаграмму автоматически на каждое изменение класса. Это визуальный шум, который скрывает архитектурно важные сдвиги.

## Итоговая проверка набора

Перед публикацией ответьте:

- Понятно ли нетехническому читателю назначение системы и её граница по Context?
- Можно ли по Container понять, какие приложения, хранилища и внешние системы участвуют в работе?
- Детализированы ли только действительно сложные containers и сценарии?
- Все ли стрелки имеют направление и содержательную подпись?
- Совпадают ли названия с требованиями, сценариями, UML-моделями и ADR?
- Различены ли логические containers, экземпляры в deployment и технические классы?
- Может ли читатель перейти по ссылке от обзорной C4-карты к нужной подробной модели?

Используйте также [официальный checklist C4](https://c4model.com/diagrams/checklist). Если на вопрос нельзя ответить по текущему набору, добавляйте не «ещё одну диаграмму», а конкретное представление, которое закрывает этот вопрос.
