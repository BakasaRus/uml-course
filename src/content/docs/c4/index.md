:::note[TL;DR]
C4 помогает рассказать об уже спроектированной программной системе на нескольких уровнях приближения: от её контекста до важных частей реализации. Это не замена UML, требований или архитектурных решений, а карта, связывающая их для конкретной аудитории.
:::

В проекте часто есть требования, сценарии, диаграммы классов, компоненты и схема развёртывания, но новому участнику всё равно трудно ответить на простой вопрос: **как устроена система в целом?** Одна большая диаграмма не решает проблему: она смешивает пользователей, классы, базы данных, серверы и детали протоколов.

C4 предлагает не одну «диаграмму архитектуры», а согласованный набор небольших представлений. Каждое отвечает на свой вопрос и показывает только нужную детализацию.

## Что такое C4

C4 — notation-independent подход к описанию архитектуры программной системы. Он задаёт иерархию абстракций, но не предписывает форму прямоугольников, цвета или инструмент. Подробные рекомендации опубликованы на [официальном сайте C4](https://c4model.com/diagrams/).

| Уровень | Область | Главный вопрос |
| --- | --- | --- |
| System Context | одна программная система среди людей и внешних систем | кому и зачем нужна система, с чем она взаимодействует? |
| Container | одна программная система | из каких приложений и хранилищ она состоит? |
| Component | один выбранный container | как внутри него распределена существенная функциональность? |
| Code | один выбранный component | какими техническими элементами реализована важная часть? |

Здесь **container** означает приложение или хранилище данных, необходимое для работы системы. Это не обязательно Docker-контейнер. **Component** — группа связанной функциональности за понятным интерфейсом; он не обязан совпадать с UML-компонентом, пакетом или каталогом исходного кода.

## Основные и дополнительные представления

Для большинства небольших ИС достаточно двух диаграмм: System Context и Container. Они рекомендованы авторами C4 как базовый набор. Остальные представления строят, только если они помогают принять решение, обнаружить проблему или объяснить существенную часть системы.

| Представление | Когда добавлять | Что не показывать вместо него |
| --- | --- | --- |
| System Landscape | нужно показать портфель систем организации | одну выделенную проектируемую систему |
| Component | container стал слишком сложным для обсуждения одним блоком | каждый класс и внутренний вызов |
| Code | важный component нельзя объяснить существующей технической моделью | весь исходный код |
| Dynamic | сложный сценарий требует показать архитектурное взаимодействие | все сценарии подряд |
| Deployment | важны конкретное окружение и размещение экземпляров | логическое разбиение на containers |

## C4 в маршруте курса

C4 начинается не с рисования. Его элементы выводятся из уже построенных материалов:

```text
граница и стейкхолдеры
→ требования и сценарии
→ предметная и техническая модели
→ проектные решения и архитектура
→ C4-представления
```

- [Стейкхолдеры и граница системы](/modelling/stakeholders-and-boundary) дают людей, ответственность и внешние системы для Context.
- [Программная архитектура и слои](/modelling/software-architecture-and-layers), [архитектура данных](/modelling/data-architecture) и [системная архитектура](/modelling/system-architecture-and-deployment) дают containers и их связи.
- [Проектные решения и ADR](/modelling/project-decisions) объясняют, почему границы и технологии выбраны именно так.
- [Согласованность и трассируемость](/modelling/model-consistency-and-traceability) проверяет, что архитектурная карта не противоречит остальной модели.

## Сквозной пример

Дальше используется сервис записи на консультации. Одна и та же система последовательно раскрывается так:

```text
Context: студент, преподаватель, сервис записи, SSO, сервис уведомлений
Container: веб-приложение, backend API, БД, отдельный worker уведомлений
Component: Booking, Schedule, Notification, SSO Adapter внутри backend API
Code: BookingService, BookingRepository, Booking и ConsultationSlot
```

Каждый последующий уровень уточняет один элемент предыдущего. Нельзя добавить новый внешний сервис только на Component diagram или поместить в Deployment view container, которого нет в статической архитектуре.

## Правила чтения и оформления

Диаграмма должна быть понятна без устного рассказа. Минимальные правила из [рекомендаций C4 по нотации](https://c4model.com/diagrams/notation):

- заголовок называет тип диаграммы и её область;
- легенда объясняет форму, цвет, границу и иконки;
- у каждого элемента есть тип, имя и краткая ответственность;
- у containers и components явно указана технология, если она существенна;
- каждая связь направлена и подписана глаголом или содержательным описанием;
- связь между containers содержит протокол или технологию взаимодействия, когда это важно;
- сокращения понятны аудитории или раскрыты в легенде.

Проверить готовую диаграмму помогает [официальный checklist C4](https://c4model.com/diagrams/checklist).
