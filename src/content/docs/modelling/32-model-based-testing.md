:::note[TL;DR]
Модель даёт не только рисунок решения, но и условия проверки: допустимые объекты, разрешённые переходы, альтернативы сценария и наблюдаемые результаты. Из каждого существенного правила можно получить проверку модели и затем проверку реализации.
:::

## Зафиксировать вариант модели

Ниже используется вариант справочника: создание сразу подтверждает запись; резервирование интервала, сохранение записи и outbox выполняются в одной транзакции. В базовом примере лекций создание оставляет статус `Создана`, поэтому ожидаемый результат теста будет другим. Выберите один вариант и зафиксируйте его в [контракте системной операции](/notation/system-sequence-diagrams#контракт-системной-операции).

## Проверки структуры

Используйте [диаграмму объектов](/notation/object-diagrams), чтобы предъявить модели конкретные данные. Укажите полный набор объектов и связей, иначе отсутствие связи на частичном рисунке нельзя автоматически считать нарушением.

| Правило | Допустимый снимок | Недопустимый снимок |
| --- | --- | --- |
| запись принадлежит одному студенту | одна запись и один связанный студент | одна запись связана с двумя студентами |
| интервал хранит историю | отменённая и подтверждённая записи одного интервала | запрет такой истории кратностью `0..1` |
| активна максимум одна запись | одна `Confirmed`, остальные `Cancelled` | две `Confirmed` одного интервала |

Проверка структуры должна включать и случай с отсутствующим обязательным значением. Набор примеров для инварианта приведён в [OCL](/notation/constraints-and-ocl#сквозной-пример-одна-активная-запись).

## Проверки жизненного цикла

Для автомата записи составьте таблицу: исходное состояние, событие, guard, ожидаемое состояние, эффект. Например, для уже существующей записи:

| Начало | Событие | Ожидание |
| --- | --- | --- |
| `Создана` | подтверждение при зарезервированном интервале | `Подтверждена` |
| `Подтверждена` | отмена до завершения консультации | `Отменена`, интервал освобождён, запись сохранена в истории |
| `Отменена` | подтверждение той же записи | статус остаётся `Отменена`; контракт операции возвращает отказ |
| `Подтверждена` | завершение до окончания интервала | переход блокируется guard; статус прежний |

При проверке **покрытия состояний** посетите каждое существенное состояние. Для **покрытия переходов** выполните каждый разрешённый переход хотя бы раз. Отдельно проверьте ложные guards и запрещённые последовательности: одних успешных переходов недостаточно. Внешний отказ определяется контрактом операции; отсутствие стрелки в автомате не генерирует его автоматически.

Проверьте также различие внутреннего перехода и самоперехода: счётчики `entry` и `exit`, запуск и прекращение `doActivity` могут выявить ошибку, скрытую одинаковым итоговым статусом.

## Проверки сценария и взаимодействия

| Случай | Что воспроизвести | Что наблюдать |
| --- | --- | --- |
| свободный интервал | один запрос записи | подтверждённая запись и задание outbox существуют до успешного ответа |
| занятый интервал | уже есть активная запись | отказ; новая запись и новое задание не созданы |
| ошибка общей транзакции | сбой после резервирования, до фиксации | резервирование, запись и outbox откатились вместе |
| сбой доставки | worker не смог отправить уведомление | запись по-прежнему подтверждена; сбой доставки учитывается отдельно |
| конкурентные попытки | два запроса на один свободный интервал с управляемым перекрытием выполнения | ровно один успех, другой конфликт; активных записей не более одной |

Последний случай нельзя надёжно проверить двумя последовательными вызовами или случайной задержкой. В тесте реализации синхронизируйте попытки у существенной границы и проверяйте состояние постоянного хранилища. Ограничение на классовой диаграмме выражает требование, но не является механизмом конкурентной защиты.

Для последовательности проверяйте только существенный порядок: сохранение и фиксация до успешного ответа, отсутствие уведомления об успехе после конфликта. Не закрепляйте тестом каждое внутреннее обращение, если другой порядок сохраняет контракт. Примеры допустимых трасс — в [расширенных взаимодействиях](/notation/sequence-advanced#сравнить-допустимые-трассы).

## Проверки процесса

Для activity-диаграммы пройдите каждую альтернативу решения, завершение каждой параллельной ветви и значимые способы прерывания. У каждого шага должны появиться требуемые входные токены. Контрпример «одна альтернативная ветвь пришла в `join`, другая никогда не запустится» позволяет обнаружить остановку без программного кода.

Покрытие ветвей не означает проверки всех сочетаний циклов и параллельных событий. Ограничьте область проверки: например, цикл с нулём, одним и несколькими элементами, если все эти размеры разрешены контрактом. Для цикла `(2, 2)` ноль итераций является нарушением, а не положительным граничным случаем.

## Связать проверку с источником

Минимальная запись проверки: идентификатор правила → элемент модели → исходные данные → действие → ожидаемый результат. При изменении правила обновляются связанные примеры, сценарии и тесты. В таблице трассируемости можно добавить столбец «Проверка», не создавая отдельную большую документацию.

Этот подход не требует автоматической генерации тестов из UML. Он помогает проверить смысл до реализации и затем сохранить его в проверках продукта. Основа — [согласованность и трассируемость](/modelling/model-consistency-and-traceability); короткие задания для работы вручную — в [практикуме UML](/notation/exercises).
